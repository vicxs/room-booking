# Errors as Problem Details (RFC 9457)

Every API error is an `application/problem+json` body following RFC 9457, declared in the Contract as a shared `Problem` schema so the generated TypeScript client types it. Errors the HTTP status already explains (400, 404) use `type: about:blank`; each business rule the client must tell apart gets its own `type` of the form `urn:room-booking:problem:<slug>` (e.g. `room-name-taken`); validation errors add an `errors` extension, a list of `{field, message}`. Messages are in English and come from the backend. We chose the standard over a home-made `{code, message}` shape, which would reinvent the same thing, and over Spring Boot's default error body, which is not part of the Contract and cannot be typed; Spring 6's `ProblemDetail` supports it natively.
